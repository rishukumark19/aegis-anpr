# PROJECT RESEARCH & DEVELOPMENT BRIEF # AI-Powered Vehicle Identification & Monitoring System (ANPR) ## 1. PROJECT BACKGROUND We currently operate a camera/CCTV-related business and want to expand into AI-powered surveillance and vehicle identification solutions. The proposed product is an Automatic Number Plate Recognition (ANPR) system designed primarily for Indian vehicles. The objective is to use existing CCTV/IP cameras wherever possible, identify vehicles automatically, extract their registration numbers, and maintain a searchable database of vehicle movements. We want to develop this into a product that can eventually be installed and sold to: - Apartments and gated communities. - Commercial buildings and offices. - Hotels and hospitals. - Shopping malls and parking facilities. - Industrial premises. - Private campuses and other secured properties. ### Primary business objective Instead of selling only CCTV cameras and installation services, we want to offer a complete smart surveillance solution with AI-based vehicle identification, monitoring, reporting and access management. --- ## 2. WHAT WE WANT TO BUILD The system should perform the following workflow: 1. An IP camera continuously captures vehicles. 2. The system receives the camera's video stream. 3. AI detects a vehicle. 4. AI identifies the number plate. 5. OCR extracts the registration number. 6. The system validates and corrects common character recognition errors. 7. The system records the vehicle's information. 8. A dashboard allows an administrator to search and monitor vehicle activity. Example: A car enters a gated community. The system automatically records: - Registration number: KA03MN1234 - Date: 31 October 2026 - Entry time: 10:42:15 AM - Camera: Main Gate Camera 01 - Vehicle type: Car - Captured vehicle image. - Captured number plate image. - Recognition confidence. - Entry/exit status, if supported by the installation. The administrator should be able to search for KA03MN1234 and see its previous recorded movements. Important: The system must distinguish between a detected plate and a verified registration number. A syntactically valid number is not necessarily a correctly recognized number. --- ## 3. EXISTING OPEN-SOURCE PROJECTS TO INVESTIGATE We do not want to build everything from scratch. First, investigate existing GitHub projects, their source code, pretrained weights, documentation, dependencies, licensing and actual working condition. The goal is to reuse suitable existing implementations wherever possible. ### A. Indian Number Plate Recognition GitHub: https://github.com/subash9940/indian-number-plate-recognition What it offers: - Indian number plate detection. - YOLO-based plate detection. - ByteTrack vehicle tracking. - Fine-tuned TrOCR for Indian plate reading. - Indian registration format correction. - Multiple-frame OCR voting. - Video processing. - CSV output. Why investigate: This is particularly relevant because it is designed for Indian registration plates rather than generic international plates. Important restrictions: - The repository uses AGPL-3.0. - Its fine-tuned TrOCR weights are marked non-commercial due to the training dataset's licensing. - Its published OCR evaluation uses a small test set and is not a production accuracy guarantee. Do not use its existing OCR weights commercially without appropriate permission. ### B. Indian ANPR – ByteTrack + FastAPI GitHub: https://github.com/bhavyabundela06/Indian-ANPR-ByteTrack-FastAPI What it offers: - Indian vehicle number plate recognition. - YOLO-based detection. - ByteTrack vehicle tracking. - PaddleOCR integration. - Indian registration format correction. - FastAPI backend. - SQLite database. - Streamlit dashboard. - RTSP camera configuration. - Vehicle detection logs. Why investigate: This project already has several elements of the system we eventually want to build. It can help us understand how the recognition engine, backend and dashboard communicate. Known limitations mentioned by its author: - Prototype rather than production-ready. - No authentication on its API endpoints. - Incomplete vehicle metadata persistence. - Single-threaded processing. - Limited production scalability. - Hardware requirements need testing. Treat it as a reference implementation, not a finished product. ### C. ANPR India GitHub: https://github.com/vrajiah/ANPR-India What it offers: - YOLOv5 number plate detection. - PaddleOCR text recognition. - NorFair vehicle tracking. - Indian number plate validation. - Video and image processing. - CSV output. - Streamlit web interface. - Docker deployment configuration. Why investigate: This is another useful end-to-end implementation that combines detection, OCR, tracking and basic reporting. The repository declares MIT licensing. However, independently verify the licences of its bundled and external dependencies, pretrained weights and training datasets before commercial reuse. ### D. OpenALPR GitHub: https://github.com/openalpr/openalpr What it offers: - Open-source ANPR engine. - C++ implementation. - Image and video processing. - Python, Node.js, Java, Go and other bindings. - Existing recognition infrastructure. Why investigate: It is an established ANPR project and can be useful for understanding existing recognition implementations. Limitations: - Its main repository is older. - Its original recognition pipeline is not specifically optimized for modern Indian registration plates. - It uses AGPL-3.0 licensing. - Commercial licensing and compatibility need careful evaluation. Do not automatically select it as our primary engine. --- ## 4. OPEN-SOURCE TECHNOLOGIES TO INVESTIGATE We should evaluate individual components separately instead of assuming one GitHub repository is the final answer. ### A. Computer Vision and Detection **YOLO** Purpose: - Detect vehicles. - Detect number plates. - Identify bounding boxes. - Process video frames. Documentation: https://docs.ultralytics.com/ GitHub: https://github.com/ultralytics/ultralytics Important licensing consideration: Ultralytics offers AGPL-3.0 and Enterprise licensing. Its official guidance states that proprietary commercial deployments require an Enterprise licence unless the applicable AGPL obligations are met. Do not build a closed-source commercial product around Ultralytics without first resolving this licensing issue. Investigate alternative detection frameworks and models with commercially compatible licences. ### B. OCR – Optical Character Recognition **PaddleOCR** GitHub: https://github.com/PaddlePaddle/PaddleOCR Purpose: - Extract characters from number plate images. - Recognize letters and numbers. - Process cropped plate images. - Provide confidence information. Why investigate: - Apache-2.0 licensed project. - Can run locally. - No requirement to pay a hosted OCR API when self-hosted. - Supports multiple languages and text recognition workflows. Check the exact model weights and dependencies selected. ### C. Image Processing **OpenCV** GitHub: https://github.com/opencv/opencv Documentation: https://docs.opencv.org/ Purpose: - Read video streams. - Extract frames. - Crop number plates. - Resize images. - Improve contrast. - Reduce image noise. - Process night-time footage. - Prepare images for OCR. OpenCV 4.5.0 and later uses Apache-2.0 licensing. ### D. Vehicle Tracking **ByteTrack** GitHub: https://github.com/ifzhang/ByteTrack Purpose: - Track a vehicle across multiple frames. - Avoid repeatedly counting the same vehicle. - Associate multiple plate readings with one vehicle track. - Improve recognition through multiple observations. Verify the repository's licence and compatibility with the selected detection framework. ### E. Backend and Database Investigate: - Python. - FastAPI. - PostgreSQL. - SQLAlchemy. - Redis, if required for background processing. - WebSockets for live dashboard updates. ### F. Frontend Investigate: - React. - TypeScript. - Tailwind CSS. - Recharts for analytics. - WebSockets for live updates. The dashboard should be simple enough for non-technical property managers and security staff. --- ## 5. CAMERA AND HARDWARE REQUIREMENTS A major requirement is compatibility with cameras we already sell or install. We should investigate whether an ordinary IP CCTV camera can be used without purchasing a dedicated ANPR camera. ### Camera compatibility Investigate: - RTSP video stream support. - ONVIF compatibility. - IP camera integration. - Main stream and sub-stream support. - Camera authentication. - Multiple camera connections. - Network connectivity. - Recording/NVR integration. The system should preferably support existing cameras from brands such as: - Hikvision. - CP Plus. - Dahua. - Other RTSP/ONVIF-compatible IP cameras. Do not assume every camera from these manufacturers supports every required feature. ### Camera positioning and specifications Investigate the importance of: - Camera resolution. - Lens and focal length. - Shutter speed. - Vehicle speed. - Capture distance. - Camera angle. - IR illumination. - Day/night performance. - Motion blur. - Weather conditions. - Plate size in the captured frame. A dedicated ANPR camera may be necessary for certain installations. We should compare the cost and performance of ordinary CCTV cameras against dedicated ANPR cameras. ### Development hardware Our available development laptop: - Windows 11. - AMD Ryzen 7 8845HS. - NVIDIA RTX 4060 Laptop GPU. - 8 GB VRAM. - Radeon 780M integrated graphics. Use this machine for the initial development and testing. Evaluate CUDA compatibility, VRAM requirements, model size and performance. Do not assume a system requiring 16–32 GB VRAM is necessary without benchmarking a smaller configuration first. ## 6. PROPOSED SOFTWARE ARCHITECTURE We want a modular architecture that allows us to replace individual AI models without rebuilding the complete application. Proposed architecture: CAMERA / NVR ↓ RTSP VIDEO STREAM ↓ VIDEO CAPTURE SERVICE (Python + OpenCV) ↓ VEHICLE DETECTION ↓ NUMBER PLATE DETECTION ↓ PLATE IMAGE CROPPING AND PREPROCESSING ↓ OCR RECOGNITION ↓ INDIAN REGISTRATION FORMAT VALIDATION ↓ MULTI-FRAME TRACKING AND CONFIDENCE SCORING ↓ BACKEND API (FastAPI) ↓ DATABASE (PostgreSQL) ↓ REACT ADMIN DASHBOARD ### Important architectural decisions 1. Camera capture and AI inference should be separate services. 2. The application should support multiple cameras. 3. Processing should happen locally wherever possible. 4. The system should not depend on paid cloud APIs. 5. The recognition engine should be replaceable. 6. The database should retain both the recognized number and supporting evidence. 7. The system should not save every frame unnecessarily. 8. The application should support both recorded video and live camera streams. 9. Backend and frontend should communicate through documented APIs. 10. The application should support future deployment on an on-premise server. Do not unnecessarily introduce microservices, Kubernetes or complicated infrastructure for the first prototype. --- ## 7. EXPECTED APPLICATION FEATURES ### A. Dashboard Create a clean administrative dashboard showing: - Total vehicles detected. - Vehicles detected today. - Unique vehicles today. - Current camera status. - Recent vehicle detections. - Entry and exit counts. - Recognition failures. - Camera connection status. ### B. IMPORTANT INDIAN NUMBER PLATE REQUIREMENTS The system must be optimized for Indian registration plates. Investigate the following formats and variations: - Standard state registration plates. - Two-letter state codes. - Different RTO code lengths. - Private vehicles. - Commercial vehicles. - Bharat Series (BH). - Temporary registration plates. - Two-line number plates. - Different plate colours. - Motorcycles and scooters. - Cars, buses and trucks. The recognition system should not simply reject a plate because it does not match one standard regular expression. Implement validation as a configurable layer, with support for different legitimate formats. Investigate common OCR character confusion: - O and 0. - I and 1. - B and 8. - S and 5. - Z and 2. Use multiple frames to improve recognition confidence. Do not automatically change an uncertain registration number without retaining the original OCR output. --- ## 9. TESTING AND PERFORMANCE REQUIREMENTS This is one of the most important parts of the project. A model that reads a few static photographs is not necessarily suitable for a real CCTV installation. We need to test: ### Different lighting conditions - Bright daylight. - Direct sunlight. - Shadows. - Low light. - Complete darkness. - IR illumination. - Headlights pointing towards the camera. ### Different vehicle conditions - Stationary vehicles. - Slowly moving vehicles. - Fast-moving vehicles. - Motorcycles. - Cars. - Commercial vehicles. - Partially obstructed plates. - Dirty or damaged plates. ### Different camera conditions - Different camera resolutions. - Different capture distances. - Different camera angles. - Different focal lengths. - Different video frame rates. - Different compression levels. ### Metrics to measure - Plate detection precision. - Plate detection recall. - OCR exact-match accuracy. - Character-level accuracy. - False recognition rate. - Missed plate rate. - Processing FPS. - End-to-end recognition latency. - GPU and CPU utilization. - Performance with multiple cameras. Important: Separate detection accuracy from OCR accuracy. A correct OCR result on a manually cropped plate does not prove that the entire camera-to-recognition pipeline works accurately. Build a labelled test dataset using authorized Indian vehicle footage. --- ## 10. SECURITY, PRIVACY AND LEGAL REQUIREMENTS This product processes vehicle registration numbers and potentially identifiable footage. Research applicable Indian privacy and data-protection requirements, including the Digital Personal Data Protection Act and applicable rules. The application should support: - Authorized camera access. - User authentication. - Role-based permissions. - Secure password storage. - Encrypted communication. - Secure camera credentials. - Audit logs. - Configurable footage retention. - Configurable plate-record retention. - Secure deletion. - Restricted access to vehicle search. - Protection against unauthorized API access. Avoid collecting unnecessary personal information. Do not assume that a registration number can be used to retrieve an owner's identity from a public API. Do not attempt unauthorized access to government vehicle-registration databases. The initial system should identify and record plates from authorized camera footage, not identify vehicle owners. --- ## 11. DEPLOYMENT OPTIONS Investigate two deployment models. ### Option A: Local / On-Premise Deployment The software runs on a computer or server installed at the customer's premises. Advantages: - No compulsory cloud subscription. - Video remains within the customer's network. - Local processing. - Lower ongoing cloud costs. - Works without continuous internet access. This should be the first deployment model to investigate. ### Option B: Cloud-Connected Deployment The AI engine runs locally, but the dashboard and selected records can be accessed remotely through a secure cloud-connected system. Possible advantages: - Central management. - Multiple customer installations. - Remote monitoring. - Centralized reports. - Subscription-based software model. Do not stream all raw camera footage to the cloud unnecessarily. Design the application so cloud connectivity can be added later. --- ## 12.
